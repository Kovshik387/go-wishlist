# Master prompt: Telegram Mini App для вишлистов

Ты — senior product engineer и UI/UX designer. Создай с нуля production-ready MVP Telegram Mini App для создания и отслеживания вишлистов.

Рабочее название продукта: **WishTrack**. Название, логотип и цвета должны быть вынесены в конфигурацию, чтобы их можно было легко заменить.

## Контекст продукта

Приложение по смыслу похоже на followish.io:

- пользователь создаёт один или несколько вишлистов;
- добавляет желания вручную или по ссылке на товар;
- делится вишлистом с друзьями;
- друзья могут подписаться на пользователя и забронировать подарок;
- подписчики получают сообщение от Telegram-бота, когда пользователь добавил новое желание;
- владелец вишлиста по умолчанию не видит бронь и имя забронировавшего, чтобы сохранить сюрприз.

Не копируй название, логотип, иллюстрации, тексты или точную компоновку followish. Сделай самостоятельный продукт, вдохновлённый его лёгкостью, дружелюбностью и простым сценарием «создать → поделиться → получить подарок».

## Главная задача

Собери реально работающий монорепозиторий:

- backend на Go;
- Telegram-бот;
- Telegram Mini App;
- PostgreSQL;
- фоновые Telegram-уведомления через transactional outbox;
- Docker-конфигурация для локального запуска и деплоя на сервер;
- миграции, тесты и документация.

Не ограничивайся прототипом, моками или одной HTML-страницей. Все основные сценарии MVP должны работать end-to-end.

## Технологический стек

### Backend

- Go, версия из существующего `go.mod`;
- `net/http` + `chi`;
- PostgreSQL + `pgx`;
- SQL-запросы через `sqlc`;
- миграции через `golang-migrate`;
- структурированные логи через `log/slog`;
- конфигурация только через environment variables;
- Telegram Bot API через небольшой типизированный HTTP-клиент без тяжёлого bot framework;
- OpenAPI 3.1 как контракт REST API.

### Frontend

- React + TypeScript + Vite;
- Telegram Mini Apps SDK;
- TanStack Query для server state;
- React Hook Form + Zod для форм и валидации;
- CSS variables и CSS Modules или аккуратно настроенный Tailwind;
- mobile-first, но с качественной адаптацией до desktop web;
- русский язык как основной, архитектура готова к i18n.

### Инфраструктура

- PostgreSQL 16+;
- S3-compatible storage для загруженных изображений, MinIO для локальной разработки;
- multi-stage Dockerfile;
- `compose.yaml` для локального запуска;
- пример production-конфигурации с Caddy и HTTPS;
- один backend-бинарник с режимами `api`, `worker` и `migrate`.

Не добавляй Redis в MVP: очередь и дедупликация должны работать на PostgreSQL.

## Авторизация и Telegram-интеграция

1. Mini App получает `Telegram.WebApp.initData` и отправляет его backend.
2. Backend обязательно валидирует подпись `initData` по официальному алгоритму Telegram и проверяет свежесть `auth_date`.
3. Никогда не доверяй `initDataUnsafe`.
4. После успешной проверки создай или обнови пользователя по `telegram_id`.
5. Выдавай короткоживущий access token и безопасный refresh token в `HttpOnly`, `Secure`, `SameSite=Lax` cookie. Frontend и API должны обслуживаться с одного origin.
6. При первом запуске объясни ценность уведомлений и вызови `requestWriteAccess`. Отказ не должен блокировать работу приложения; покажи способ включить уведомления позже через `/start` у бота.
7. Bot webhook должен проверять `X-Telegram-Bot-Api-Secret-Token`.
8. Обработай команды `/start`, `/app`, `/notifications`, `/help`.
9. Поддержи deep links вида `https://t.me/<bot>/<app>?startapp=wishlist_<public_token>`.
10. Telegram ID хранить как `BIGINT`; нигде не приводить его к 32-битному типу.

## Сценарии MVP

### 1. Первый запуск

- пользователь открывает Mini App;
- проходит Telegram-авторизацию без email и пароля;
- видит короткий onboarding из 2–3 экранов;
- выбирает отображаемое имя, при наличии используется Telegram avatar;
- даёт или отклоняет разрешение на сообщения от бота;
- попадает на экран ленты.

### 2. Создание вишлиста

Поля:

- название;
- короткое описание;
- emoji или обложка;
- повод: день рождения, свадьба, Новый год, новоселье, другое;
- необязательная дата события;
- видимость: публичный, только по ссылке, приватный;
- разрешить/запретить бронирование;
- показывать/скрывать владельцу факт бронирования — по умолчанию скрывать.

### 3. Добавление желания

Два режима:

- по URL;
- вручную.

Поля желания:

- URL товара;
- название;
- описание/комментарий;
- изображение;
- цена и валюта;
- приоритет: обычный или «очень хочу»;
- количество;
- необязательные параметры: размер, цвет, вариант.

При вставке URL backend пытается получить Open Graph metadata: заголовок, картинку, цену и домен магазина. Пользователь всегда может исправить результат вручную.

URL fetcher обязан быть защищён от SSRF:

- только `http` и `https`;
- запрет loopback, link-local, private и reserved IP ranges после DNS resolution;
- повторная проверка адреса после каждого redirect;
- лимиты на redirects, timeout и размер ответа;
- проверка Content-Type;
- безопасный User-Agent;
- никакого доступа к cloud metadata endpoints.

### 4. Публичный вишлист и шаринг

- у каждого доступного по ссылке вишлиста есть криптографически случайный `public_token`, а не последовательный ID;
- кнопка «Поделиться» открывает нативный Telegram share flow;
- получатель открывает конкретный вишлист по `startapp`;
- доступный по ссылке вишлист открывается без ручного поиска пользователя;
- приватный вишлист доступен только владельцу;
- отозванная ссылка перестаёт работать после ротации токена.

### 5. Подписки и лента

- можно подписаться и отписаться от другого пользователя;
- можно отдельно отключить уведомления от конкретного пользователя, не отписываясь;
- лента показывает новые желания пользователей, на которых подписан текущий пользователь;
- сортировка — сначала новые;
- карточка содержит автора, вишлист, фото, название, цену, приоритет и время добавления;
- из карточки можно открыть товар, вишлист, забронировать желание или сохранить копию в свой список.

Не показывай в ленте желания из приватных и доступных только по ссылке списков, если пользователь не получил доступ через ссылку. Для MVP автоматические уведомления подписчикам отправляй только о желаниях из публичных списков.

### 6. Бронирование подарка

- пользователь может забронировать и отменить бронь;
- операция транзакционная и защищена от двойного бронирования;
- другие гости видят, что желание занято;
- владелец списка по умолчанию не видит статус и автора брони;
- тот, кто забронировал подарок, всегда видит собственную бронь;
- нельзя бронировать собственное желание;
- удаление желания корректно завершает или архивирует связанную бронь;
- история действий сохраняется для аудита, но не раскрывается владельцу через API.

### 7. Telegram-уведомления

Когда пользователь добавляет желание в публичный вишлист:

- создай domain event в той же транзакции, что и желание;
- положи событие в transactional outbox;
- worker находит активных подписчиков с разрешёнными уведомлениями;
- каждому создаётся дедуплицированная задача доставки;
- бот отправляет сообщение с автором, названием желания, ценой при наличии и inline-кнопкой «Открыть желание»;
- сообщение ведёт в Mini App по deep link;
- ошибки Telegram API повторяются с exponential backoff и jitter;
- `403 bot blocked` отключает доставку этому пользователю;
- `429` учитывает `retry_after`;
- соблюдай Telegram rate limits;
- повторная обработка события не должна создавать дубли.

Если один автор добавил несколько желаний за короткое время, объедини уведомления в digest, например: «Аня добавила 4 новых желания». Окно агрегации должно настраиваться, значение по умолчанию — 5 минут.

Настройки уведомлений:

- глобальное включение/выключение;
- новые желания;
- новые вишлисты;
- напоминания о приближающемся событии;
- mute конкретного автора;
- тихие часы с учётом timezone пользователя.

Не уведомляй владельца о бронировании, если он явно не включил такую настройку.

## Модель данных

Минимальные таблицы:

- `users`;
- `user_sessions`;
- `wishlists`;
- `wishes`;
- `follows`;
- `follow_notification_settings`;
- `wishlist_access`;
- `reservations`;
- `notification_preferences`;
- `activity_events`;
- `outbox_events`;
- `notification_deliveries`;
- `processed_telegram_updates`;

Обязательные требования:

- UUID или UUIDv7 для внутренних сущностей;
- отдельный случайный public token для share links;
- `created_at`, `updated_at`, soft delete там, где нужен аудит;
- уникальные constraints для follow и активной reservation;
- индексы под feed, outbox polling, followers и public token;
- UTC в базе, timezone пользователя хранить отдельно;
- optimistic locking или проверка версии для конфликтных обновлений.

## Архитектура backend

Используй понятное разделение:

```text
cmd/
  app/
internal/
  auth/
  bot/
  config/
  httpapi/
  wishlist/
  wish/
  follow/
  reservation/
  notification/
  media/
  store/
  platform/
migrations/
openapi/
web/
deploy/
```

Правила:

- бизнес-логика не зависит от HTTP handler;
- транзакции начинаются в application/service layer;
- repository interfaces вводи только там, где они упрощают тестирование;
- ошибки имеют стабильные machine-readable codes;
- request ID проходит через логи;
- graceful shutdown для API и worker;
- фоновые задачи захватываются через `FOR UPDATE SKIP LOCKED`;
- обработчики и worker должны быть идемпотентными.

## Безопасность и приватность

- лимиты размера JSON и upload;
- whitelist MIME types и перекодирование изображений;
- rate limiting для auth, URL preview, mutations и webhook;
- CORS только для настроенного origin;
- security headers;
- параметризованные SQL-запросы;
- secrets не попадают в git, логи или frontend bundle;
- редактирование и удаление только владельцем;
- полный privacy check на каждом read endpoint;
- журналирование критичных действий без чувствительных данных;
- endpoint удаления аккаунта с понятной политикой удаления/анонимизации;
- не логировать raw `initData`, bot token, refresh token и signed URLs.

## Наблюдаемость

- JSON logs;
- метрики количества HTTP-запросов, ошибок, outbox lag, notification success/failure;
- `/healthz` проверяет процесс;
- `/readyz` проверяет PostgreSQL и готовность миграций;
- в README опиши резервное копирование PostgreSQL и S3.

## Тесты

Обязательны:

- unit test проверки Telegram `initData` с валидной, неверной и устаревшей подписью;
- privacy tests для public/link/private wishlist;
- тест, что владелец не получает скрытые reservation fields;
- конкурентный integration test двойного бронирования;
- тест идемпотентности outbox и Telegram delivery;
- тесты mute, quiet hours и digest;
- SSRF tests для loopback, private IP, DNS/redirect cases;
- frontend component tests для основных форм;
- минимум один Playwright happy path.

Тесты должны быть детерминированными. Время, UUID и Telegram client подменяй через явные зависимости.

## Definition of Done

Работа завершена, когда:

1. `docker compose up` поднимает приложение и зависимости.
2. Пользователь входит через валидный Telegram `initData`.
3. Можно создать список и желание вручную или по URL.
4. Можно поделиться deep link и открыть конкретный список.
5. Можно подписаться на пользователя.
6. Новое публичное желание создаёт outbox event и Telegram-уведомление подписчику.
7. Уведомление содержит рабочую кнопку возврата в Mini App.
8. Бронь защищена от гонки и скрыта от владельца по умолчанию.
9. Все privacy modes соблюдаются на backend.
10. Миграции, тесты, линтеры и production build проходят.
11. Нет секретов, моковых API и критичных TODO.
12. README позволяет новому разработчику запустить проект без догадок.

## Порядок работы

1. Изучи существующий репозиторий и сохрани совместимость с уже принятыми решениями.

6. Добавь тесты, Docker и документацию.
